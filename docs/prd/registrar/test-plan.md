# Test Plan — Tela de Registro (`/registrar`)

> URL: `http://localhost:3001/registrar`
> Backends reais: `sgsm` core `:8080` (`POST /v1/api/medicos` e `/v1/api/pacientes`, ambos públicos), `ms-sboot-auth` `:8081` (`POST /v1/api/auth/registrar`) — sem mocks.
> Fluxo: para tipo MEDICO/PACIENTE, o front primeiro cria o registro de domínio (`medicoService.cadastrar`/`pacienteService.cadastrar`, chamadas públicas) e só depois cria a conta de login (`authService.registrar`), em duas chamadas HTTP separadas sem transação entre elas.
> Executado em: 2026-08-20, ao vivo via Playwright MCP contra `http://localhost:3001` + backends reais `sgsm` (:8080) e `ms-sboot-auth` (:8081). Sem mocks. Ver `docs/prd/registrar/qa-results.md` para o relatório completo e `docs/prd/registrar/evidence/` para screenshots + payloads de rede.

## Achados suspeitos de bug crítico — verificar com prioridade

- [x] **REG001 — CRÍTICO, muito provável**: registrar tipo **Funcionário** provavelmente está totalmente quebrado. O front-end não envia `referenciaId` para esse tipo (comentário no código diz "resolvido automaticamente pelo backend via e-mail"), mas `AuthService.registrar()` no `sgsm-auth` exige `referenciaId != null` para qualquer perfil que não seja DESENVOLVEDOR, incluindo FUNCIONARIO, e lança `IllegalArgumentException("referenciaId é obrigatório para o perfil FUNCIONARIO")` antes de qualquer lookup por e-mail. Testar: preencher email + senha com tipo Funcionário e submeter → confirmar se aparece esse erro (ou algum outro) e se é IMPOSSÍVEL concluir o cadastro por esse caminho — **PARCIALMENTE REFUTADO por prova real.** Lendo o código-fonte real de `AuthService.java` (não a suposição), o método `registrar()` tem um caminho dedicado: `if ("FUNCIONARIO".equals(tipoPerfil) && referenciaId == null) { busca EntidadeAuth por email+tipo }`. Não existe a `IllegalArgumentException` hipotetizada. Testado ao vivo em dois cenários: (1) e-mail SEM funcionário pré-cadastrado por um médico → `POST /auth/registrar` retorna `404` com `"Nenhum funcionario encontrado com email: ..."` (`evidence/REG001-func-sem-cadastro.png`); (2) e-mail COM funcionário pré-cadastrado (via `/funcionarios`, por um médico logado) → registro **funciona normalmente**, `201 Created`, login subsequente confirma `perfil: FUNCIONARIO` e `referenciaId` correto (`evidence/REG001-REG035-func-sucesso.png`, `evidence/REG033-035-func-login.png`). Ou seja: o fluxo de Funcionário **não está quebrado**, mas depende de um pré-requisito não documentado na tela (um médico precisa ter cadastrado o funcionário antes, em `/funcionarios`) — sem isso, a mensagem de erro (404 "nenhum funcionário encontrado") é tecnicamente correta mas pouco amigável para quem tenta se cadastrar sem essa etapa prévia.
- [x] **REG002 — CRÍTICO, muito provável**: registro de **Médico** ou **Paciente** faz duas chamadas HTTP sequenciais sem rollback: 1) cria o registro em `/medicos` ou `/pacientes` (sucesso, 201), 2) cria a conta de login em `/auth/registrar`. Se a segunda falhar (ex.: e-mail já usado por OUTRO perfil no sgsm-auth), o registro de domínio da etapa 1 já foi persistido e fica órfão — cadastrado no sistema mas sem login para acessá-lo. **Repro sugerido**: registrar como Paciente com e-mail X com sucesso completo; depois tentar registrar como Médico usando o MESMO e-mail X (com CRM novo/diferente) → verificar se o `POST /v1/api/medicos` é aceito (já que unicidade de e-mail lá é só entre médicos) e SÓ DEPOIS o `POST /v1/api/auth/registrar` falha com "Email já cadastrado" — se isso acontecer, o médico órfão criado é um bug real, documentar com as duas evidências de rede — **CONFIRMADO por prova real.** Passo 1: registrado Paciente "QA Registro Orfao Paciente" com e-mail `qa.registro.orfao@teste.com` → `POST /pacientes` 201 (id `4dc88cd8-...`), `POST /auth/registrar` 201 (conta PACIENTE criada), login confirmado funcionando (`evidence/REG002-step1-paciente-sucesso.png`). Passo 2: registrado Médico "QA Registro Orfao Medico" (CRM 888099/SP, novo) com o MESMO e-mail → `POST /medicos` retorna **201 Created** (médico persistido, id `7fade4fe-d704-40e1-8570-6a510500755d`), e a chamada seguinte `POST /auth/registrar` retorna **409 Conflict** (`"Email ja cadastrado: qa.registro.orfao@teste.com"`) (`evidence/REG002-step2-medico-orfao.png`). O usuário vê apenas o toast de erro e acha que nada foi criado, mas o médico "QA Registro Orfao Medico" ficou permanentemente órfão no banco do `sgsm` — sem conta de login, sem forma de ser acessado por essa tela.
  > **RETESTE (Rodada 2) — CORRIGIDO E CONFIRMADO.** `RegisterPage.tsx` agora chama `authService.emailDisponivel(email)` (`GET /v1/api/auth/email-disponivel`, público) ANTES de criar o registro de médico/paciente. Repro real: Paciente "QA Registro Retest Paciente Orfao" cadastrado com sucesso (`qa.retest.orfao.r4.20260820@teste.com`); tentativa seguinte de cadastrar Médico "QA Registro Retest Medico Orfao" (CRM 999188/SP) com o MESMO e-mail foi bloqueada ANTES de qualquer chamada — rede mostra apenas `GET /auth/email-disponivel` (200, `disponivel:false`), **nenhum `POST /v1/api/medicos` foi disparado**. Toast: "Este e-mail já está cadastrado. Faça login ou use outro e-mail." Evidência: `evidence/REG002-step1-paciente-sucesso-retest.png`, `evidence/REG002-step2-medico-bloqueado-retest.png`, `evidence/REG002-retest.log`.

## Submissão — edge cases de robustez

- [x] **REG028 — BUG confirmado (edge case previsto no plano)**: Duplo clique no botão "Criar conta" com formulário válido — verificar quantas requisições são disparadas (sem guard visível no código contra duplo submit; pior ainda aqui por serem DUAS chamadas em sequência — um duplo clique poderia gerar até 2 médicos/pacientes duplicados antes do primeiro completar). Confirmado: dois cliques disparados via DOM (`btn.click(); btn.click();`) sem nenhum guard de front-end geraram **duas** chamadas `POST /v1/api/pacientes` simultâneas. Pior do que o esperado: uma delas retornou **500 Internal Server Error** cru (`"Erro interno. Tente novamente mais tarde."` — race condition não tratada graciosamente, ao contrário do 400 limpo de REG024) e a outra completou com 201 + criou a conta de login normalmente. O usuário não percebe o erro 500 de fundo porque a segunda tentativa "salva" o fluxo com o toast de sucesso. `evidence/REG028-duplo-clique.png`.
  > **RETESTE (Rodada 2) — CORRIGIDO E CONFIRMADO nas duas camadas.** Front: `RegisterPage.tsx` agora tem guard síncrono `enviandoRef` contra duplo submit. Repetido o mesmo `btn.click(); btn.click();` síncrono na mesma tick com formulário válido → rede mostra **apenas 1** `GET /auth/email-disponivel`, **1** `POST /v1/api/pacientes` (201) e **1** `POST /v1/api/auth/registrar` (201), não 2. Confirmado também via banco: nova tentativa de criar paciente com o mesmo CPF retornou 400 "CPF já cadastrado", provando que existe só um registro. Backend: teste complementar de concorrência real (duas requisições `POST /pacientes` simultâneas via curl, mesmo CPF, sem guard de front no caminho) confirmou que a que perde a corrida recebe **400 limpo** ("CPF já cadastrado"), nunca mais 500 cru — `GlobalExceptionHandler` agora trata `DataIntegrityViolationException` como 400. Evidência: `evidence/REG028-duplo-clique-guard-retest.png`, `evidence/REG028-retest.log`.
